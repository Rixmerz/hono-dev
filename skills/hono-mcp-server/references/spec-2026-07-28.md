## 1. Transport — Streamable HTTP

Source: <https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http.md>

### The endpoint

- The server MUST provide a single HTTP path (the MCP endpoint) that supports POST.
- Every client message is its own POST. The body is one JSON-RPC request or notification;
  the client MUST NOT send JSON-RPC responses.
- The client MUST send `Accept` listing both `application/json` and `text/event-stream`.
- A notification the server accepts gets `202 Accepted` with no body; one it cannot accept
  gets an HTTP error status such as `400`. (This revision defines no client-to-server
  notification over Streamable HTTP; closing the SSE response stream is the cancellation signal.)
- A request gets either `Content-Type: application/json` (one object) or
  `Content-Type: text/event-stream` (an SSE stream scoped to that request).
- On an SSE stream the server MAY send notifications related to the request, MUST NOT send
  independent JSON-RPC requests, and SHOULD end the stream with the final response. Closing the
  stream MUST be treated as cancellation of that request.
- SSE responses SHOULD carry `X-Accel-Buffering: no`. (Not checked against the SDK's streamed
  responses in this session: confirm with `curl -i` on a tool that streams.)
- Long-lived change notifications come from a `subscriptions/listen` request, whose response
  stream stays open; request-scoped notifications (`notifications/progress`,
  `notifications/message`) never use it.

### What a 2026-07-28-only server does with 2025 traffic

Section "Earlier Streamable HTTP Revisions" (anchor `#backward-compatibility`): a server that
supports only this revision SHOULD answer

- `GET` or `DELETE` to the MCP endpoint with `405 Method Not Allowed`;
- an `Mcp-Session-Id` header by ignoring it, and never minting or echoing session ids;
- a `Last-Event-ID` header by ignoring it.

A server MAY support both eras on one endpoint. Versioning page, "Backward Compatibility with
Initialization-Based Versions": a request with modern per-request `_meta` is served statelessly;
an `initialize` request selects legacy semantics for that session.

### Security

- Servers MUST validate the `Origin` header on all incoming connections (DNS rebinding). A
  present, invalid `Origin` gets `403 Forbidden`; the body MAY be a JSON-RPC error with no `id`.
- Locally, servers SHOULD bind only to `127.0.0.1`, not `0.0.0.0`.
- Servers SHOULD implement proper authentication for all connections.

### Request metadata (headers mirrored from the body)

Anchor `#request-metadata`.

| Header | Source | Required |
|---|---|---|
| `MCP-Protocol-Version` | `_meta["io.modelcontextprotocol/protocolVersion"]` | every POST; value MUST match the body |
| `Mcp-Method` | `method` | all requests |
| `Mcp-Name` | `params.name` or `params.uri` | `tools/call`, `resources/read`, `prompts/get` |

- Header names are case-insensitive; header values are case-sensitive.
- A value that is not plain ASCII is carried as `=?base64?<base64 of UTF-8>?=`, and the server
  MUST decode it before comparing it with the body.
- Anchor `#server-validation`: a missing or mismatching header makes the server answer
  `400 Bad Request` with JSON-RPC error `-32020` (`HeaderMismatch`).
- Unknown protocol version: `400` with `UnsupportedProtocolVersionError` (`-32022`) listing the
  supported versions. Unknown RPC method: `404` with JSON-RPC error `-32601`.
- A tool may mirror parameters into `Mcp-Param-{Name}` headers via `x-mcp-header` in its
  `inputSchema` (optional for servers; clients MUST honour it). A server that processes the body
  MUST check those headers against the body.

## 2. Versioning and discovery

Sources: <https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md>,
<https://modelcontextprotocol.io/specification/2026-07-28/server/discover.md>

- There is no handshake: each request declares its version, and the server accepts or rejects
  each one independently.
- Unsupported version, error shape:

```json
{ "jsonrpc": "2.0", "id": 1,
  "error": { "code": -32022, "message": "Unsupported protocol version",
             "data": { "supported": ["2026-07-28", "2025-11-25"], "requested": "1900-01-01" } } }
```

- Servers MUST implement `server/discover`. Its result has `supportedVersions`, `capabilities`,
  `_meta["io.modelcontextprotocol/serverInfo"]` (SHOULD be included; self-reported, not for
  security decisions) and optional `instructions`. The operation supports caching.

## 3. Authorization

Sources: the authorization pages listed at the top. Authorization is OPTIONAL for MCP; when an
HTTP server supports it, it SHOULD conform to this spec.

### Roles

The MCP server is an OAuth 2.1 resource server; the client is an OAuth 2.1 client; the
authorization server is separate or co-hosted and out of scope.

### What the server MUST implement

1. **Protected Resource Metadata** (RFC 9728). The document MUST include `authorization_servers`
   with at least one entry.
2. **At least one** way to publish where that metadata lives (clients MUST support both):
   - `WWW-Authenticate: Bearer resource_metadata="<url>"` on `401` responses; or
   - a well-known URI, either at the path of the MCP endpoint
     (`https://example.com/.well-known/oauth-protected-resource/public/mcp` for
     `https://example.com/public/mcp`) or at the root
     (`https://example.com/.well-known/oauth-protected-resource`).
3. **Validate access tokens** as an OAuth 2.1 resource server and check they were issued
   **for this server** (audience, RFC 8707). Invalid or expired tokens get `401`.
4. Accept `Authorization: Bearer <token>` on every request; never accept a token in the query string.
5. **Never pass the client's token through** to an upstream API; an upstream API gets its own token.

### Errors

| Status | Meaning |
|---|---|
| 401 | authorization required or token invalid |
| 403 | invalid scopes or insufficient permissions |
| 400 | malformed authorization request |

Insufficient scope at runtime (SHOULD): `403` with
`WWW-Authenticate: Bearer error="insufficient_scope", scope="<scopes>", resource_metadata="<url>"`,
listing all scopes the operation needs in one challenge. Servers MUST account for scope
hierarchies. `scope` in a `401` challenge is a SHOULD; the client treats it as authoritative
for the current operation. Anchors `#scope-selection-strategy`, `#scope-challenge-handling`.

### What the client does (so you can test it)

Client flow: request without a token, read `resource_metadata` from the `401`, fetch the
metadata, discover the authorization server (RFC 8414, then OpenID Connect Discovery, in the
priority order of the discovery page), register (Client ID Metadata Documents preferred;
Dynamic Client Registration is deprecated), run the authorization-code flow with PKCE `S256`
and the `resource` parameter, then call the MCP endpoint with the bearer token. Clients MUST
validate a present `iss` against the recorded issuer (RFC 9207) before redeeming the code.

### Security considerations that land on the server

Token audience binding (the server MUST validate tokens were issued for it), token theft
(short-lived tokens; secure storage), access token privilege restriction (reject tokens whose
audience does not include this server), confused deputy (a proxy server using static client
ids MUST get user consent per dynamically registered client).

## 4. Other changes in the revision (from the changelog)

- MRTR: servers return `InputRequiredResult` (`resultType: "input_required"`) with
  `inputRequests`; clients retry the original request with `inputResponses`.
- Every result carries `resultType` (`"complete"` for ordinary results).
- `ttlMs` and `cacheScope` ("public" or "private") required on `tools/list`, `prompts/list`,
  `resources/list`, `resources/read` and `resources/templates/list`. `server/discover` also
  "supports caching" (its example carries both fields) but the changelog does not list it as required.
- `tools/list` SHOULD return tools in a deterministic order.
- Resource not found is now `-32602`; MCP-reserved error codes are `-32020` to `-32099`.
- Tasks moved out of the core into the `io.modelcontextprotocol/tasks` extension.
- Removed: `ping`, `logging/setLevel`, `notifications/roots/list_changed`. Log level is now
  per-request in `_meta` (`io.modelcontextprotocol/logLevel`).
- Deprecated: Roots, Sampling, Logging; the HTTP+SSE transport; Dynamic Client Registration.
